Design System · Case Study

One source of truth:
rebuilding Agora's design system.

Agora's design system lived in Figma but had fallen out of date, and nothing connected it to the code engineers shipped. As Design System Lead, I ran the rebuild: a two-tier token foundation, around 65 components rebuilt across Figma and a new Storybook, and a review process that kept design and code in step. All over a single quarter, with four designers contributing alongside their product work and our Frontend Lead.

Role Design System Lead Team 4 designers + Frontend Lead Tools Figma · Storybook · Notion

The problem

A design system in name only

Agora had a design system that existed on paper. It lived in Figma, it was out of date, it looked visually weak, and it was full of gaps. No variables. No consistent theme. No primitives, no tokens.

There was also no Storybook and nothing shared between design and development. So engineers rebuilt components from scratch, each one slightly different from the last. The same button shipped in several visual versions, and the product drifted out of sync with itself. With nothing connecting the two sides, inconsistency wasn't a slip. It was the default outcome of how we worked.

Why it was worth solving

Why it needed a real fix

The drift showed up everywhere: duplicated components in code, mismatches between Figma and production, and slow, repetitive UI work. It would only compound as the product grew. I made the case for fixing it at the foundation rather than patching symptoms, and took ownership of the rebuild.

Slower shipping

Every new screen meant rebuilding pieces we already had.

Harder onboarding

No single place that said "this is how we build."

Lost coherence

The interface quietly drifted as the product scaled.

The approach

One reference for design and code

There was no Storybook before this, so the frontend team stood up a new one alongside the system. It became the shared reference: every component implemented there, with its states and props wired into a live controls panel, so design and development work against the same thing instead of two files that drift.

Keeping the two in sync was the real work, because nothing was automated. Changes went through my design review first, then to the developer responsible for Storybook to implement. It took constant communication and manual coordination, but it is what kept Figma and the shipped code matching.

What we built

Foundations first, then everything on top

01Foundations

We started with the layer everything depends on: a two-tier token system, with primitives (raw values) feeding semantic tokens (how those values are used). We spent real time on the semantic naming with the frontend developers, so the structure made sense in both Figma and code.

We deliberately chose not to support light and dark mode. The product had no multiple themes and none were planned, so building for them would only add complexity it didn't need.

The structure wasn't right from day one. We started with fairly generic semantic names, and as we applied them to real components we found some weren't specific enough. So we added more component-specific tokens where they helped, instead of forcing everything into one generic scheme. We refined it through implementation, together with engineering.

02Audit & rebuild

With the tokens in place, we took every existing component, rebuilt it on the new foundation, and brought it up to a consistent visual standard: correct states, spacing, and tokens, no one-off values. Around 65 components in all.

03Storybook

Every component also lives in Storybook, with its states and props wired into the controls panel so anyone can test it live and QA the real coded version.

Quality

Reviewed in the product, not just in Figma

A component wasn't done when it looked right in isolation. Each one was reviewed for its states and variants, correct token usage, alignment between Figma and code, accessibility, and documented behavior. Where it helped, we looked at how mature design systems solved the same problem instead of reinventing a pattern.

The step that mattered most was dropping components into real product screens. That regularly surfaced edge cases and constraints we'd missed in the library, so we went back and refined them. It's the difference between components that work in a design file and ones that hold up in the product.

The shift

How the system changed

Before, the same UI got rebuilt in slightly different ways across the product. Now, screens are assembled from one shared set of components.

How I led it

Running it end to end

This is the part I owned most directly. I ran the whole initiative from a single Notion tracker, every component with a status and an owner, split across four designers who were contributing alongside their regular product work. Each component moved through a review loop I owned, and I worked with the Frontend Lead daily to keep Figma and Storybook in step.

I designed more than 20 of the roughly 65 components myself. Beyond that, my job was to hold a consistent standard across everyone's contributions, approve each component, refine our shared conventions, and make the calls that needed one owner. The hard part wasn't any single component. It was keeping the work moving and the bar steady while everyone, me included, still had product work to ship.

Adoption & migration

Getting it into the product

New screens are now built only from the refined components, so they're consistent by default. For the existing product, each designer owns their domain and migrates old components to the new ones, prioritized sprint by sprint, with PMs aligned on the process. The system is spreading through the product instead of sitting in a file.

Impact

What the system changed

A more consistent product. The clearest change is coherence. Parts of the product used to look and behave differently. Now they share one set of components and patterns, so the UI feels far more unified.
Less rebuilding. Designers now have proper, reusable components instead of recreating UI from scratch for every screen. That makes everyday design work more straightforward and takes much of the effort out of keeping things consistent.
A process, with owners. The system runs on a real process: tracker, review, visual QA, and handoff to Storybook, with clear owners and buy-in from design, development, and product.
A foundation to build on. New work starts from the system instead of a blank canvas, onboarding is easier, and it's become the base the rest of our design work stands on.

I don't have reliable metrics for time saved or adoption, so I'm describing what's changed in how we work rather than putting numbers on it.

An unexpected payoff

A foundation for AI prototyping

A real token foundation turned out to be what made AI prototyping genuinely useful here. I built a skill that carries the design system, its tokens, components, and connectors, so AI-generated prototypes come out built from real components instead of generic UI. The team is starting to use it, and it's a good example of the foundation paying off beyond cleaning up today's screens.

What's next

Where it goes next

The system is intentionally still growing. Next is expanding component coverage and, because we work in agile cycles, refining existing components as we learn what holds up and what doesn't. Every variable change still runs through the frontend team, so Storybook stays in sync.
