Design System · Case Study

One source of truth:
rebuilding Agora's design system.

How I led the move from an outdated Figma kit to a living design system in Figma and Storybook, one shared source of truth that design and development actually build on. Around 65 components, rebuilt on a new token foundation over a single quarter.

Role Design System Lead Team 4 designers + Frontend Lead Tools Figma · Storybook · Notion

The problem

A design system in name only

Agora had a design system that existed on paper. It lived in Figma, it was out of date, it looked visually weak, and it was full of gaps. No variables. No consistent theme. No primitives, no tokens.

Worse, there was no Storybook and no shared source of truth between design and development. So engineers rebuilt components from scratch, each one a little different from the last. The same button existed in several visual versions, and the product slowly drifted out of sync with itself. Inconsistency wasn't an accident here. It was built into the way we worked.

Why it was worth solving

Structural, not cosmetic

The drift showed up everywhere: duplicated components in code, mismatches between Figma and production, and slow, repetitive UI work. It was only going to compound as the product grew, so I stepped up to lead the fix at the root.

Slower shipping

Every new screen meant rebuilding pieces we already had.

Harder onboarding

No single place that said "this is how we build."

Lost coherence

The interface quietly drifted as the product scaled.

The reframe

A system, not a prettier file

A better looking Figma file would not have solved this. The real fix was a single source of truth that design and development share.

We chose Storybook as that anchor. It gives developers an interactive workshop to build and test components in isolation, and it gives designers a live catalog to verify that the final code matches the exact spec. Instead of endless back and forth over pixel measurements and hidden states, anyone can open the Storybook URL, tweak variables, stress-test edge cases, and run visual QA on the real coded components.

What we built

Foundations first, then everything on top

01Foundations

We started with the layer everything else depends on: a proper variable and token system built in two tiers, primitives (the raw values) feeding semantic tokens (how those values are used). This took many rounds of discussion and hard decisions that I led with my team, until we had a structure we trusted enough to build the rest of the system on.

02Audit & rebuild

With variables in place, we took every existing component, rebuilt it on the new tokens, and refined it visually so it finally looked the way it should. Around 65 components in all, audited and rebuilt.

03Storybook

Every component now lives in Storybook as well as Figma, with all of its states, use cases, and properties wired into the controls panel so anyone can stress-test it live. The goal was never just coverage. It was a Storybook that is easy to read and genuinely useful, not a dumping ground of one-off examples.

The shift

How the system changed

How I led it

One tracked path, my review at the center

This is the part I owned most directly. I organized the whole initiative in a single Notion tracker, every component with its status and owner, split across the team of four. Each component moved through a loop I ran end to end, and I worked side by side with the Frontend Lead every day to keep it moving, made the calls that needed a decision-maker, and built a number of the components myself.

Adoption & migration

A system only matters if people use it

New screens are now built only from the refined components, so everything ships consistent and visually stronger by default. For the existing product, each team member owns their domain and is migrating old components to the new ones, prioritized sprint by sprint, with PMs fully aligned on the process. The system is spreading across the product, not sitting in a file.

Impact

What the system changed

Faster shipping. Developers assemble screens from tested, reusable components instead of building from scratch. Around 65 components were rebuilt on the new foundation in a single quarter.
Consistency. One source of truth means design and code match. Duplicated components are gone, and the product looks unified and more polished.
Adoption & ownership. A governed process (tracker, review, visual QA, documented handoff) with clear owners and buy-in from design, dev, and product.
Scale. Onboarding is easier, and the system is now the foundation the rest of our work stands on.

An unexpected payoff

A foundation for AI prototyping

With a real design system in place, prototyping with AI got dramatically better. We built a skill that carries the full design system, its connectors and its knowledge, so AI-generated prototypes come out looking like the real product, built from real components. The system did not just clean up today's UI. It made a faster way of designing possible.

What's next

A living system, not a finished artifact

The system is intentionally still growing. Next is expanding component coverage, and because we work agile, refining existing components as we learn what works and what doesn't. Every variable change goes through the frontend team so Storybook stays perfectly in sync.
